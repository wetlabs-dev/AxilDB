# Care Queue refinement — November 25, 2026

## Outcome and release notes

The search field and View now share one responsive row. Search submits explicitly through its icon or the keyboard, never per keystroke; populated searches have a clear link. The location count shares a wrapping row with Expand all and Collapse all. Location names and paths wrap in a dedicated header row; completion and workflow actions have matching 44 px targets below on mobile. Categories use the same canonical icon, tint, foreground and border tokens as task badges, with a checkmark and stronger outline for the selected filter. Temporal filters remain distinct.

View dismisses on outside pointer/touch, Escape, Close, navigation or a successful explicit save/reset/startup-mode change. Automatic grouping/order saves keep the settings open so multiple changes are easy. Failures retain selections and expose retry within the open settings. Success feedback uses one replaceable, four-second live status overlay, not a permanent toolbar item. Native select interactions remain inside the disclosure; listeners and notification timers are cleaned up.

## Attention investigation

The original calculation is `careQueueSummary` in `lib/care-queue-view.ts`: remove completed items, then count items whose taskType is HEALTH_CHECK or QUARANTINE_REVIEW. `components/CareQueueView.tsx` supplies **all collection queue items before category, location and search filters**, so the number does not describe the filtered visible tasks. It is dynamically derived on initial load and updated by the existing optimistic queue/snapshot store, not a separately stored or cached total.

`getCareQueue` in `lib/care-queue.ts` supplies the records:

- Scheduled GENERAL_INSPECTION cadences become HEALTH_CHECK obligations. The active definition/instance cadence, latest completed care and initial-care anchor determine their due dates. An unresolved non-pest condition suppresses that plant’s routine general-inspection obligation in favor of condition follow-ups.
- OPEN / IMPROVING non-pest conditions on ACTIVE instances become individual HEALTH_CHECK follow-ups, using severity, latest check and explicit follow-up dates. Pest conditions become PEST_CHECK and do not contribute.
- ACTIVE quarantines on ACTIVE instances become QUARANTINE_REVIEW tasks using their target-release dates.
- Queue keys are deduplicated before calendar planning. Multiple condition records and a quarantine on one plant legitimately contribute multiple tasks. This is not a unique-plant count or a join-row count.

Future, due-today and overdue dates all contribute; scheduling conflicts are not removed from this total. Therefore it can overlap both Due today and Overdue (and Overdue itself is included in Due today). Propagation-type instances can contribute if they have a health obligation or quarantine, but PROPAGATION_CHECK tasks contribute only to Props. Quiet rules, disabled adjustments and snoozes retain their existing queue-generation semantics; the metric counts the resulting active obligations.

Missing metadata, unresolved repotting windows, incomplete cadence configuration and missing history are **not independently counted as issues**. A missing history anchor can affect when a real cadence task is generated, but there is no “missing history” increment. Archived/deceased/inactive instances are excluded from these health/condition/quarantine queries. Reminder records always become REMINDER, even if their prose concerns health, so they do not inflate Attention. Every source is scoped to the active collection.

**Finding:** the calculation is internally consistent but the label is insufficiently explained. No aggregation defect was found and no business semantics were redefined. A total of 146 can legitimately represent future routine inspections plus condition follow-ups and quarantine reviews. Production data was not accessed, so this report does not claim a breakdown of that specific 146.

A controlled fixture verifies three health/quarantine tasks across one plant (a future condition follow-up, another overdue condition follow-up, and a future quarantine review), with one overlap in Overdue. An additional water task contributes to Due today without changing Attention, and a completed health task is excluded.

The entire Attention metric is a touch/keyboard button opening a compact native dialog. Its explanation says: “Outstanding health checks and quarantine reviews across this collection, including future dates. Counts tasks, not unique plants; routine inspections and condition follow-ups are included. Filters do not change this total. Some tasks also count as due or overdue.” It directs users to Health and explicitly says this is not a count of unhealthy plants or missing configuration. A possible future label is “Health & quarantine tasks”; the existing label is retained with the verified explanation.

## Root cause and corrected completion workflow

Previously `CareQueueLocationBoard` linked Complete visible care to `/care/bulk?locationId=...&includeNested=1`. That workflow defaults to one care category and chooses plants, not outstanding obligations. No task identities, search constraint or category constraint survived the shortcut. This was inappropriate route reuse, not a limitation of the canonical individual care-recording service.

The button now opens an in-context native dialog using the **logical filtered section’s item keys**. It does not inspect DOM visibility and still works on collapsed groups. Parent grouping includes the tasks actually represented by the parent group; Flat paths uses the exact section. Search, category and location filters have already constrained that list. Future, projected, completed or conflicted tasks are shown as unavailable, never silently included. New tasks appearing later are not added to the review.

The review independently selects each obligation, so watering and pest inspection for one plant are two rows. It shows botanical names, IDs, due dates, paths, badges, selected-task/unique-plant counts and category counts, with Select all / Deselect all. All currently eligible rows start selected. Shared and per-task notes are supported. Fertilizer uses the authoritative assigned recipe and optional strength/dose/water-volume fields. Repotting requires the same new substrate choice and recipe validation as individual completion; its confirmation is disabled until those choices are supplied. No care is recorded on opening.

Treatment steps, condition assessments and quarantine release decisions retain their existing required specialist workflows. They remain visible with an explanation and an Open task link rather than being recorded as generic OTHER care. A condition cannot silently be declared resolved, and a treatment cannot bypass safety/product/photo requirements. Routine inspection and all other directly completable queue activities use the canonical Complete behavior. Bulk care by location remains the separate, unchanged proactive single-category workflow and can still include care that was not due.

## Service, identity, transaction and retry architecture

`lib/visible-care.ts` owns the shared eligibility boundary and 100-task limit. `lib/visible-care-service.ts` exposes reusable `reviewVisibleCare` and `completeVisibleCare` functions. `POST /api/care/complete-visible` uses existing origin/authentication/collection-logger requirements, private no-store responses and a bounded request body (250,000 characters).

Review request: `{collectionSlug, action:"review", keys:[...]}`. Response: `{review:[{item, occurrence, unavailable}]}`. Completion request: `{collectionSlug, action:"complete", entries:[{key,occurrence,fields:{...}}], sharedNote, operationId, issuedAt}`. Response includes `results` per key (`completed` / `already-completed`, optional eventId), completed/alreadyCompleted counts and distinct plants. Notes/field values are limited to 4000 characters; only explicitly supported completion fields are accepted. The total payload limit can require shorter notes or a smaller selection.

The deterministic occurrence fingerprint covers the key, due date, schedule anchor, last completion, location, condition update, assigned recipe/substrate recommendation, recurrence and quiet-day context. A stable task key alone cannot identify a recurring occurrence. Submission regenerates the authoritative queue **once** under the existing exclusive collection calendar lock and verifies every selected occurrence/eligibility and active plant before writing. Moves, changed schedules, completion, snoozes and exclusions invalidate the review instead of substituting future care. IDs and event types come from the authoritative item, not arbitrary client fields.

Execution is sequential inside **one atomic transaction**, bounded at 100 tasks and the existing 30-second transaction timeout. Each row invokes `applyCareQueueMutation(..., 'complete', ...)`, preserving care history, audit/domain events, cadence clearing, substrate/repot side effects, timestamps and same-day duplicate checks. It does not insert simplified parallel care events or modify definition cadences. Existing condition/treatment/quarantine services are not bypassed.

The existing `executeCareOperation` receipt and payload hash protect double taps, same-ID concurrent requests, expired actions and retries after a lost response. Successful retries return the committed result. Different-ID stale submissions cannot complete the next occurrence. If any validation or row mutation fails, **the entire batch rolls back**; there are no committed partial successes to retry. Client requests have a 45-second confirmation timeout and are aborted on unmount; uncertain confirmations retain the same receipt identity on retry. The review preserves entered data (including when explicitly refreshing matching rows), freezes the failed attempt payload and offers Retry same selection or Refresh review. Network uncertainty does not mean a new operation should be issued: retry uses the original identity. A stale review must be refreshed before changed work can be confirmed.

After confirmation, there is one coordinated store reconciliation (including its existing forecast snapshot), not a browser request per task. Grouping, filters, search, expansion state and scroll context remain in place. The review closes only after confirmation; server refresh failure uses existing recovery behavior. Successful feedback distinguishes completed tasks from same-day already-recorded care. Care/audit events remain per obligation as required; forecast/schedule regeneration is not invoked once per mutation.

## Verification, performance and limitations

Use the disposable `localhost:55444/axildb_care_view` database only. `check:visible-care` covers mixed events, multiple tasks on one plant, shared/task notes, atomic required-substrate rollback, exact receipt retry/concurrent retry, stale occurrences, foreign/missing keys, scheduling changes and batch limits. Controlled batch sizes 1, 5, 20, 50 and 100 are measured without production load testing. The UI suite covers outside touch/Escape/save dismissal, transient feedback, selected counts, independent deselection, actual event types, search/category scope, failure/retry, one browser batch request, queue reconciliation, narrow layouts and access checks. Existing preference and queue/calendar/color/workflow regressions are also run.

Native dialogs provide modal keyboard focus and Escape; disclosure controls retain accessible states, explicit labels and Close. Existing fonts, theme tokens and botanical rendering are reused. Light/dark and 320/390/1440 px browser layouts are inspected. This is not physical iOS PWA, hardware screen-reader or virtual-keyboard certification. No native-device permission behavior is changed. Exhaustive browser execution of every specialist workflow is outside this refinement; its task-specific UI is preserved.

The synchronous cap intentionally rejects larger logical groups instead of silently truncating. Narrow by category/search/location to work in smaller groups. No new worker, queue system, connection pool or cache was introduced. Measurements are local service timings, not internet latency, production capacity, CPU profiling or query-count claims.

Deploy via **Web deployment**. No database migration, host configuration, environment variable or deployment-agent change is required. New receipts use the existing operation table. No production collection data was accessed or modified.

### Recorded results

- Typography checks, standalone TypeScript and production build passed. Targeted lint comparison against the starting commit found no new findings; existing query-builder lint warnings are unchanged. The build retains the existing Browserslist-age notice.
- Saved-view unit/database tests passed, including isolation and 80 concurrent updates. Saved-view browser regressions passed across reload, new session/context, URL precedence, failure/retry and operational return links.
- Mixed-care service tests passed. The final measured transactional completion durations were 32 ms (1 task), 47 ms (5), 112 ms (20), 218 ms (50) and 449 ms (100). They include authoritative validation and care recording, but not network latency or the separate client refresh. A previous full run also passed; this is not a production capacity benchmark.
- Existing actual care-operation, optimistic queue, calendar/Quiet Day, category-token/contrast and workflow checks passed. The batch UI suite passed selection, search/category scope, real event records, retry, one POST per confirmation and queue update, plus mobile outside-tap and save dismissal. No browser exceptions were recorded.
- Physical installed PWA, hardware screen readers, CPU/RAM profiling and exhaustive specialist treatment/condition/quarantine execution were not independently tested.

Matched eight-task fixture captures at 900 px viewport height show heading-to-first-card distance falling from 603 to 565 px on 390 px mobile, and 404 to 394 px on 1440 px desktop. This is a modest additional reduction after the previous hierarchy redesign; the main gains are cohesive controls and legible location actions. Task photos/cards are unchanged. Separate mixed-category captures show the checklist, individual exclusions, confirmed completion, failure/retry and both themes at 320, 390 and 1440 px. No page-level horizontal overflow was detected.
